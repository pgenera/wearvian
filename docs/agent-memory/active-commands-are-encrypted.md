**Command counter = separate "csn", 0-based for LEGACY (2026-06-06 pm, decompile-confirmed):** routing commands through the live presence session with the running HEARTBEAT counter (74,10,12…) made the vehicle reject every command and drop the link (disconnect status 0x13, no 0x17 ack). Decompile: commands use `csn` = `l60.x.r` (builder `em/f0.f`: `int i=tVar.r; tVar.r=i+1`), a SEPARATE counter from heartbeats (`l60/i0` uses `j0Var.k`). csn init by connection type (`l60.x` ctor/`a()`, table `l60.v`): LEGACY→0, PRE_CCC/CCC→1; our Gen-1 link is LEGACY so **csn starts at 0**, +1 per command, reset per fresh nonce handshake. That's why the one-shot (single cmd, csn=0) always worked. Fix landed: `VehicleSession.commandCounter` (0-based, separate from heartbeat counter), branch `wearvian-closures-via-session`. Also confirmed `s60/i0` type ids ActiveCMDRequest=0x16/ActiveCMDResponse=0x17/VehicleStatus=0x18, and inbound decrypt `s60/e.a` (IV=bytes[2..14], ct=bytes[14..], AAD=pNonce⊕vNonce) is byte-identical to our `ActiveCommandFrames.decryptInbound`. OPEN THREAD: our session only ever gets 20-byte `1801` VehicleStatus; official only ever gets 114-byte. 20B is too short to be a valid GCM VehicleStatus (20−2−12=6 < 16 tag) — official decrypt would fail on it too. So we get a "lesser" status stream persistently; cause unknown (candidate: app subscribes 0x1c CHAR_VEHICLE_STATUS, we don't). Decompile lives at /home/pgenera/wearvian/rivian-re (see [[ref-rivian-decompile-archive]]); btsnoop decoder + tests at `watch/tools/btsnoop_rivian.py`.

**RESOLVED windows/charge-port failure (2026-06-06, sleeping-truck snoop):** captured the official app on a SLEEPING R1S doing unlock → charge-port open/close → windows vent/close, decoded with `tools/btsnoop_rivian.py`. Result: **windows (0x15/0x16) and charge-port (0x36/0x37) ARE sent over BLE, byte-identical 64B `16 01` frames on char 0x20 — NOT cloud-only.** So our codes/frame are correct; they're not cloud-routed. The difference is the SESSION: the app reconnects+rehandshakes 4× while the vehicle wakes, streams 755 heartbeats(0x1b)+ranging, waits ~10s until the vehicle pushes `18 01` STATUS (vehicle awake), THEN sends commands and keeps the session running across all 5. Our `ActiveCommandManager` one-shot (connect→handshake→1 cmd→disconnect) works for unlock/lock (security module answers half-asleep) but charge-port/windows are gated on the phone being PRESENT via the sustained heartbeat+ranging session → they get a `17 01` ack (received) but body modules drop them. **Fix path: send active commands THROUGH the live presence session (like drive, PresenceService already streams heartbeats) using the RUNNING counter, not a separate one-shot.** The 0x20 channel is bidirectional+the status bus: `16 01`=command(out 64B), `17 01`=cmd-ack(in 67B), `18 01`=STATUS(in 114B, encrypted closure/lock state — subscribe 0x20 + decrypt with our session secret to read state, this is how the app "knows"; decode of the 114B plaintext fields is the next step, needs our own session for the key). Heartbeat=`[le32 counter][1B flag][32B keyed]`, counter plaintext, increments per auth msg, resets to 0 on reconnect. Full writeup appended to `docs/passive-entry-protocol.md`. Decoder is reusable: `tools/btsnoop_rivian.py` (+`tools/test_btsnoop_rivian.py`, 18 stdlib tests). This SUPERSEDES the "vehicle-side state-gate, read FAIL reply" diagnostic below.

**Sleeping-vehicle wake over BLE (2026-06-05):** there is NO BLE wake command — `WakeVehicle` has an empty BLE byte[] (`h60/r0`, `k2.WAKE_VEHICLE`) and is cloud-routed in the app. The BLE-native wake IS the heartbeat ranging session: the official app's command HCI snoop writes PhoneProfile(10 80)+SensorInformation(01)→0x20 and streams ~1099 heartbeats→0x1b, sending the command frame INSIDE that live session (same session as passive entry). Our `ActiveCommandManager` did a bare phoneId→nonce→command, so active unlock failed on a sleeping vehicle (passive worked because PresenceService runs the full heartbeat session). Attempted fix (5c91a1e) = warm up with PhoneProfile + SensorInformation + a 24-beat heartbeat burst to 0x1b before the command — but this REGRESSED active lock/unlock even on an awake vehicle, so REVERTED (73a5218). Likely cause: the vehicle tracks a per-session message counter and our command frame is hardcoded `counter=0`; as the session's FIRST message that's valid, but after 24 heartbeats (counters 0–23) a counter=0 command reads as stale/replayed and is dropped. Revisit sleeping-vehicle wake separately WITH on-vehicle test: try continuing the command counter past the heartbeat count (e.g. counter=WAKE_BEATS), or only warm up as a fallback after a first plain attempt is dropped. Active commands restored to the proven phoneId→nonce→command(counter=0) first-message flow.

A full HCI snoop (2026-06-02, official phone app, 8 discrete commands) proved the Rivian BLE **active command frames are encrypted**, not plaintext:

- **No writes to `0x18`** (`CHAR_ACTIVE_ENTRY` "RIV_MOBKEY_WRITE") at all — our app's assumed command characteristic is unused by the official app.
- Each command = a **64-byte write to char `0x20`** (`5ae32b92-eafb-471b-afe8-e88eec4a4774`, the same control/ranging channel), one per button press.
- Frame = constant 2-byte header **`16 01`** + **62 bytes high-entropy** (212/256 distinct byte values) = encrypted + authenticated. No plaintext `command+timestamp+HMAC`.
- The official **phone app does commands over BLE** (not cloud) when near the car — so the Android app contains the full BLE command crypto.

**Consequence:** cipher, key derivation, plaintext layout, and nonce can NOT be recovered from a snoop (ciphertext only) or by on-vehicle trial (can't brute-force AEAD). This invalidated the "unlock-first via snoop + on-vehicle iteration" plan and the plaintext `ActiveCommandFrames`-to-`0x18` hypothesis (the `core-crypto` `ActiveCommandFrames.kt` seam is now known-wrong; `signCommand` HMAC may not even be how commands work). The drive heartbeat (`0x1b`, 37B, per-session keyed) is in the same boat.
